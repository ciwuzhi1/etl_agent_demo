## 一句话概括本章

第 4 章让 Agent 能消费**数据库** Profile，本章把 **CSV / JSON / JSONL / XLSX / Parquet / ORC / XML / Markdown / 文本型 PDF** 九种文件接进同一条安全链路：

```
multipart 上传 → UUID 受管原文件(SHA-256) → Celery 解析 → 规范化 UTF-8 JSONL → Schema/统计/脱敏样本 → LocalFile Source 契约
```

浏览器给的文件名、编码、表头、行数、内容全都不可信，所以平台先把它变成"受管资产"：真实路径由资产 UUID 决定、写入用临时文件+原子替换、解析用固定解析器、字段名和类型由平台确定性规范化、样本进上下文前先脱敏。

关键边界一句话：**Agent 只看到别名、Schema、统计、脱敏样本和容器内只读路径，看不到原始字节、宿主机路径和内部 `file-asset://` URI**；`masked_sample` 只保护示例，规范化 JSONL 仍保留完整值，真正的数据脱敏发生在后续 SeaTunnel Transform 按已审批规则处理。

## B. 四个关键概念（大白话）

**四类"位置"为什么不能混用？** `original_filename` 给人看，API 和 Agent 都可见；`source_uri`/`normalized_uri` 是 `file-asset://<uuid>/…` 的内部定位，只有存储 Adapter 和 Worker 认识；`engine_path` 是给 SeaTunnel 容器的只读路径 `/data/file-assets/<uuid>/normalized.jsonl`。把它们分开，才可能做到"换了存储后端不改业务代码"，也才可能让响应模型物理上不含主机路径。

**上传为什么要"三段事务"而不是一个 try 块？** 第 1 段：校验身份/文件名/扩展名，写 PENDING 并提交；第 2 段：**在数据库事务外**流式落盘（否则长时间持锁）；第 3 段：新事务写 URI/字节数/SHA-256，返回 202，再投递 UUID。第 2 段失败就把资产标 FAILED；第 2 段成功但第 3 段提交失败，物理文件可能暂时成无引用对象——生产对象存储靠生命周期扫描回收。把文件系统写入伪装成可回滚的原子事务，是假的原子性。

**"统一行模型"统一的是什么？** 九种格式最终都变成 `list[dict]` + 一份 `schema_json` + 统计 + 脱敏样本 + 一份规范化 UTF-8 JSONL。但注意 §5.8 的差别：CSV/JSON/JSONL/XLSX/Parquet/ORC/XML 是**表格行**，Markdown 与文本型 PDF 是**文档元素行**。后者不能假装是表格，这正是"不支持 OCR/复杂版面"这条能力边界的落点。

**样本脱敏 ≠ 数据脱敏。** `masked_sample` 只保护进入 Agent 上下文和审查页面的那几十行；规范化 JSONL 里仍然是完整字段值，因为执行需要真数据。所以 `var/file-assets` 目录本身、只读挂载和访问控制仍是敏感边界——这一点在第 10 章做执行时才真正闭环。
