## 一句话概括本章

第 2 章把桌子搭好了，但桌上还是空的。第 3 章要往 PostgreSQL 里放进**企业事实**：谁是谁、谁属于哪个项目、这条 Pipeline 的第几版长什么样、谁批的、跑过几次、改了什么。做完之后，系统才第一次能回答"哪个版本被谁批准、哪次执行对应哪份制品"这种审计问题；也是从这一章起，`alembic` 才真正能用。

课件明确划了界：**本章只建身份、状态和持久化边界**。模型里会出现后面章节才用到的字段，那不代表连接凭据、文件资产、模型生成和执行引擎已经可用。

## B. 四个关键概念（大白话）

**为什么模型不能靠应用启动时自动建表？** `Base.metadata.create_all()` 很省事，但它只认"现在的样子"，不认"怎么变成这样"。多人在多环境推进时，没人知道库里少了哪一列、谁删了哪个索引。Alembic 把每次结构变化变成带版本号、可前滚可回滚的脚本，出问题能精确指出"卡在 0002"。

**Pipeline 与 PipelineVersion 什么区别？** 前者是那条长期存在的业务流水线（"订单同步到 Doris"），后者是它的一次**不可变**修订。需求变了不改老版本，而是开 V+1；已批准的版本要重跑，也不改老执行记录，而是新建 `ExecutionRun`。覆盖同一行 = 毁掉证据。

**项目角色和 Harness 职责为什么要分两套？** 项目角色回答"你在这个项目里算什么"（OWNER/EDITOR/VIEWER），Harness 职责回答"你能不能承担审批或提交这个动作"。二者混用会导致"项目老板自动拥有审批权"，四眼分离形同虚设。

**Bootstrap 为什么必须是一次性的？** 没有第一个用户就没人能授权别人，所以需要一个开门动作；但门开着就是任意人自称管理员的漏洞。做法是：默认关闭 → 运维短时开启并填随机 Token → 建完管理员立刻关回。测试要验的就是"第二次必须 409"。

## C. 与第 2 章的差异：为什么这一章更难

第 2 章的产物都是"进程级"的，改错了重启即可。第 3 章第一次写进 PostgreSQL 的是**结构 + 身份 + 状态规则**，一旦建错，后面 10 个章节都站在它上面；而且它同时是本章验收（C-19/C-20）的唯一客观依据。因此本章的顺序不能打乱：枚举 → 模型 → 迁移 → 身份 → 状态机 → 测试，其中迁移必须先于 Bootstrap 与成员接口。
