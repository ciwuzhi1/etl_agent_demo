## 一句话概括本章

前三章搭好了底座和企业事实，但平台对真实数据还一无所知。第 4 章打通**第一条元数据链路**：

```
API → ConnectionService → SecretProvider → Celery → ProbeRegistry → MySQL Adapter → 脱敏 Profile
```

数据工程师登记一个 MySQL 连接，密码交给 SecretProvider 加密入库，后台 Worker 用最小查询测试连通性，再探查表结构、主键、近似统计和**脱敏样本**写进 PostgreSQL。本章不生成 HOCON、不做数据同步，交付的是"后续 Agent 可以信任的最小、结构化、已脱敏的元数据上下文"。

关键边界一句话：**密码只在 Worker 调用驱动的内存里短暂存在**，不进 API 响应、审计事件、模型 Prompt 和错误日志。

## B. 三个关键概念（大白话）

**Port / Adapter / Registry 有什么区别？** Port 是"我需要一个能告诉我表结构和主键的东西"这个约定；Adapter 是某个数据库的具体实现，知道 MySQL 该查 `information_schema`、Oracle 该查 `ALL_TAB_COLUMNS`；Registry 是一张"连接器类型 → Adapter"的对照表。这样加一种数据库只新增一个 Adapter，业务代码一行不改——"支持多种数据库"不等于在服务里堆 `if/elif`。

**Profile 为什么是有时效的？** Schema 会变，统计会变。今天探到的列说明天可能就改了，所以 Profile 是"某一刻的快照"，带状态（`PENDING`/`RUNNING`/`READY`/`FAILED`）和 `expires_at`，Agent 消费它必须知道自己看的是快照而不是永久事实。

**密码为什么必须走 SecretProvider 而不是环境变量？** 环境变量是**平台自身**的配置（数据库、Redis、LLM Key），而业务数据源的凭据是**用户数据**：谁都能给项目登记一个连接，数量不定、权限各异、还要能单独轮换和销毁。它得加密进业务库并留下可审计的秘密引用，`.env` 里也不该出现它。

本章实测的明文边界，四处都查过：`encrypted_secrets.ciphertext` 里搜不到密码；`data_connections` 的 `host/options` 搜不到；`audit_events.after` 只有名称/Connector/主机/端口/库名；`var/api.log` 与 `var/worker.log` 里 `grep` 密码命中 0 次。
