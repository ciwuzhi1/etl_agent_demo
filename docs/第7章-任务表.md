## 一句话概括本章

第 6 章定义了"什么是可接受的 ETL"，本章提供**两种生成后端**：直接调用 LLM（生产路径）和 SeaTunnel CLI Orchestrator（官方黑盒），统一封装成供应商中立的 `PipelineGenerationPort` 协议，让上层状态机不用关心具体用哪个模型或引擎。

关键边界一句话：**生成器只负责产出候选 HOCON + 解释文本，不负责验证安全性（第 6 章的门禁在 policy 节点执行）、不负责持久化制品（第 9 章的版本冻结）、不负责管理生命周期（第 8 章的 AgentRunService）。**

## B. 两个关键概念（大白话）

**"Port 协议"是什么？** 就像 USB 接口，不管插的是鼠标还是键盘，电脑只认 USB 标准。这里 `PipelineGenerationPort` 就是 USB 接口，`DirectOpenAIAdapter` 和 `SeaTunnelCliAdapter` 就是鼠标和键盘。上层状态机只调用 `port.generate(request)`，不关心底层是哪个模型。

**"预算控制"防的是什么？** 防止一次生成调用耗尽所有 Token 配额或卡死太久。`BoundedConfigToolProvider` 像信用卡额度管理器：每次调用前检查剩余额度，超了就拒绝；调用后扣减额度并记录耗时。这样即使模型抽风，也不会把整个系统拖垮。

## C. 这一章的坑

| 编号 | 坑 | 证据 | 处置建议 |
|---|---|---|---|
| P7-1 | **SeaTunnel CLI 未安装**：本机只有 Docker Compose 的 SeaTunnel 容器，没有本地 CLI | `infra/compose.yaml` 里只有 `seatunnel-master` / `seatunnel-worker` 容器；`which seatunnel` 返回空 | 本章先用 direct 适配器测试，SeaTunnel CLI 适配器等装好 CLI 再验；或跳过 G7-04 的实机验证 |
| P7-2 | **LLM API 密钥未配置**：`.env` 里没有 `OPENAI_API_KEY` 或等效变量 | 当前 `.env` 只有 Fernet 密钥和数据库连接；G7-03 需要真实 API 才能实机验证 | 先用 mock 跑单元测试，实机验证等你提供 API 密钥后再补 |
| P7-3 | **Orchestrator 输出格式不稳定**：不同版本 SeaTunnel CLI 可能返回不同结构的 JSON | 参考实现用正则解析输出，但课件未明确版本号 | 适配器加容错逻辑：先尝试解析 JSON，失败则当纯文本处理；记录原始输出供调试 |
