## 一、项目定位与控制面哲学

### Q1. 用一分钟介绍一下 etl_agent_demo 这个项目

**考察点**：表达概括能力，是否真正理解自己做的系统。

**答案要点**：

- 一句话定位：面向企业 ETL 任务的智能**控制面**——理解自然语言需求、探查受管元数据、生成候选方案、请求具名审批并跟踪执行结果；真正的数据搬运交给 Apache SeaTunnel Zeta。
- 核心哲学一句话（README 原文）：**模型只负责「提建议」，从建议到真实副作用的每一道关口，都由确定性代码和具名的人把守。**
- 技术栈：Python 3.12 + FastAPI + Celery（Redis）+ PostgreSQL 17 双库 + LangGraph + SeaTunnel Zeta 2.3.13（MySQL 8 源 → Doris 3 汇）+ Vue 3 控制台。
- 核心亮点：LangGraph 六节点生成状态机、ETL 契约校验与版本冻结、四眼审批、事务 Outbox 自续投递、执行指标归一回写、Harness 内核（PDP 策略 + Tool Broker + 一次性 Capability + Ed25519 Evidence Ledger）。

### Q2. 「模型只提建议」具体怎么落实？LLM 的输出在哪些点被拦截？

**考察点**：安全边界意识，本项目最核心的设计主张。

**答案要点**：

1. **生成阶段**：LLM 产出的配置必须过 `policy` 节点的企业策略校验（`require_safe_generation_context`，`agent/graph.py`）；格式坏、策略违规、引擎 `--check` 失败都只把**已脱敏摘要**反馈给模型重修，不直接放行。
2. **契约阶段**：生成物过 ETL 契约校验（Schema 对齐、拓扑校验、Profile 快照比对，`application/schema_contract.py`）才能成为 Pipeline 版本。
3. **审批阶段**：版本一经批准冻结（制品 SHA-256），未经新的四眼审批不得改写。
4. **执行阶段**：凭据不进图状态、不进 LLM 提示词；提交给 SeaTunnel 的是物化制品，运行时由六条预算规则监督。
5. **落库阶段**：失败诊断只写脱敏文案（`application/execution_diagnostics.py`）。

### Q3. 为什么控制面和数据面分离？为什么不自己实现 ETL 引擎？

**考察点**：架构边界划分的判断力。

**答案要点**：

- 控制面做的是「理解需求、给出方案、守住关口、看清结果」，数据面做的是「高效稳定地搬运数据」——两者变更节奏、扩展瓶颈、故障域完全不同。
- 自研引擎的收益为零：SeaTunnel Zeta 已解决异构源汇连接、断点容错、分布式调度；控制面的价值在治理，不在搬运。
- 集成方式刻意收敛：控制面只经 **REST** 把已物化制品提交给 Zeta（`infrastructure/` SeaTunnel 适配器），不直连引擎内部状态；引擎侧真相统一从 `/job-info` 拉取归一。
- 类比说法：这就是 K8s 控制面 / kubelet 的关系——声明式提交 + 只读观测，执行细节外包给专用引擎。

## 二、LangGraph 编排与状态机

### Q4. 六节点状态机分别是什么？为什么这么切？

**考察点**：对编排核心的掌握程度（代码即文档，`agent/graph.py` 头部注释直接写明）。

**答案要点**：

- 六节点：`generate → clarify → repair_generation → policy → wait_for_review → failed`（`graph.py:298-303` 的 `add_node`）。
- `generate`：调用生成后端产出结构化候选（`GenerationResult`，kind 为 QUESTION / CONFIG / 其他）。
- `clarify`：模型判定需求信息不足时产出澄清问题，图进入 `WAITING_INPUT` 挂起，等人回答后恢复跑图。
- `repair_generation`：候选不完整时带反馈重新生成；`policy`：确定性企业策略 + 真实引擎 `--check` 校验；`wait_for_review`：到达审批挂起点；`failed`：确定性终态。
- 切分原则：**智能的部分（generate）只占一个节点，其余全是确定性节点**——模型被夹在确定性关口之间。

### Q5. 为什么用 LangGraph 而不是「循环 + if」或自研状态机？

**考察点**：技术选型判断（与 AgentInsight 那种自研路线相反，要能讲出这个项目选框架的理由）。

**答案要点**：

1. **流程天然有「挂起-恢复」语义**：澄清等待输入、等待人工审批都是可能持续数小时的中断，LangGraph 的 `interrupt` + Checkpoint 持久化把「停在哪、从哪继续」变成框架内建能力，自研要自己解决状态序列化与恢复一致性。
2. **图状态需要跨进程续跑**：生成在 Celery Worker 里跑，审批在 API 进程里决定——Checkpoint 库是两个进程之间的接力棒。
3. **有界修复循环**：`repair_generation` 的回边 + 修复计数器（`MAX_ENTERPRISE_REPAIR_ATTEMPTS = 2`，共三份候选总预算，`graph.py:18`）用图的路由表达「重试但禁止无限自修复」。
4. 诚实边界：README 已知边界写明 PostgreSQL Checkpoint 后端目前是占位实现（`agent/checkpoint.py` 抛 `NotImplementedError`），调用方降级到内存 Checkpoint——这是可讲的真实取舍。

### Q6. 用户补充澄清回答后，图是怎么恢复的？状态存在哪？

**答案要点**：

- `WAITING_INPUT` 状态下提交回答继续跑图；图状态存**独立 Checkpoint 库**（`ETL_AGENT_CHECKPOINT_DATABASE_URL`，与业务库分离）。
- `AgentState`（`graph.py:36`）刻意最小化：requirement、metadata_context、conversation_history、generation、phase、error、repair_count、engine_check——恢复所需字段越少，序列化与安全面越小。
- **凭据不进图状态**：运行期变量物化和真实 SeaTunnel `--check` 由 Worker 注入的 `candidate_validator` 回调完成（`build_generation_graph` 的 docstring 写明），避免敏感信息随 Checkpoint 持久化。

### Q7. 模型生成的候选格式坏了怎么办？如何防止无限自修复？

**答案要点**：

- `route_generation` 按生成结果的 kind 路由：QUESTION → clarify，CONFIG → policy，否则 → repair_generation。
- 修复不是白来：每次重修把**反馈文本**追加进 requirement（「候选完整性反馈（修复 N/2）」），要求只返回一个闭合的 ```hocon``` 代码块。
- 修复与格式错误、企业策略错误、引擎检查失败**共享同一份预算**：最多三份候选，耗尽后确定性进 failed——失败语义明确，不存在静默降级或死循环（`graph.py` `MAX_ENTERPRISE_REPAIR_ATTEMPTS`）。
- 引擎未通过时只把**已脱敏摘要**反馈给模型——真实错误细节（可能含端点、凭据线索）不出控制面。

## 三、契约校验与版本冻结

### Q8. ETL 契约校验都校验什么？

**考察点**：对「确定性把关」的具体理解（`application/schema_contract.py`）。

**答案要点**：

- 四类契约函数各守一段：`require_managed_file_source_contract` / `require_database_endpoint_contract` / `require_hdfs_file_contract`（源头合法性）、`require_profile_topology_contract`（探查拓扑）、`require_target_schema_contract`（目标 Schema 对齐）。
- **Profile 快照比对**：生成方案引用的探查画像（含 `content_sha256`，`schema_contract.py:41`）必须与当前受管元数据一致——元数据变了，旧方案即失效，防止「照着过期画像生成」。
- 校验全部是确定性代码，不问模型意见；这是「契约优先」设计：方案在成为版本之前必须先自证可执行。

### Q9. 版本冻结是怎么实现的？为什么需要？

**答案要点**：

- Pipeline 版本制品带 **SHA-256 摘要**；版本一经批准不可静默改写——要改就生成新版本、走新一轮四眼审批。
- 为什么：审批人批准的是**那一份具体制品**（hocon 配置、映射规则），不是「这个需求」；如果批准后制品还能被改写，四眼审批就形同虚设——这是审计链条的根基。
- 与执行准备衔接：提交给 SeaTunnel 的执行制品从冻结版本物化而来，执行结果可精确追溯到某个被批准的版本。

## 四、四眼审批与人机协同

### Q10. 四眼审批是怎么判定的？

**考察点**：代码级细节（`application/approvals.py:133`）。

**答案要点**：

- 申请人与审批人分离：审批动作里 `if approval.requested_by == actor_id` 直接拒绝——**同一自然人不得占用两个审批槽**。
- 审批人还须具备角色资格：项目成员中持有 `ADMIN` 或 `APPROVER` 角色才可决定（`approvals.py:139`）。
- 决定落 `decided_by`、决定时间等具名审计字段——「谁批的、什么时候批的」永久可查。
- 追问延伸：四眼不是「随便找两个人」，而是「利益分离 + 角色授权」两个独立条件的交集。

### Q11. 为什么不让模型自动判断「低风险直接执行」？人机边界怎么划？

**答案要点**：

- 低风险判断本身就是模型做的建议，让模型裁判自己的建议 = 裁判员兼运动员；项目把「是否需要审批」也做成确定性策略（`policy.py`），模型无豁免权。
- 人的角色被收敛到**最不可替代的一步**：具名批准一个冻结版本——不让人看代码细节做 yes/no，而是看契约摘要与探查画像。
- 澄清中断（WAITING_INPUT）是另一个人机协同点：信息不足时模型主动提问，而不是瞎猜配置——「问」比「猜」便宜且安全。

## 五、SeaTunnel 集成与执行观测

### Q12. 从批准的版本到 SeaTunnel 真正跑起来，链路是什么？

**考察点**：端到端链路（`application/execution_harness.py`、`execution.py`）。

**答案要点**：

1. 执行准备（execution-preparations）：从冻结版本物化制品、经 Harness 的 Prepare→Approve→Commit 流程治理；
2. 经 REST 把制品提交给 SeaTunnel Zeta（`ETL_AGENT_SEATUNNEL_API_URL`）；
3. 提交成功后经**事务 Outbox** 自续投递监控命令（`execution_tasks.py`）；
4. 监控命令周期拉取引擎 `/job-info`，直到引擎给出终态；
5. 指标归一回写 + 失败诊断 + 监督快照链。

### Q13. 事务 Outbox 的「自续投递」是怎么实现的？为什么不用轮询接口或定时任务扫表？

**考察点**：可靠投递设计的原理级理解（`application/harness_outbox.py`、`execution_tasks.py:227-284`、`harness_outbox_tasks.py:91`）。

**答案要点**：

- **Outbox 本体**：业务提交与 Outbox 命令写入同库同事务，Worker 的 `HarnessOutboxService` 认领 pending → 发送 → `mark_sent` / `mark_failed`，保证「提交成功必有监控命令」不因进程崩溃而丢。
- **自续投递**：`_enqueue_monitor` 发出的监控命令若发现引擎仍在运行，就**自己再投一条下轮命令**（`execution_tasks.py:282-284` 注释：「尚未到终态就续投下一条，形成自续轮询直到引擎收敛」）；引擎侧出现终态即停止续投，交给 `_advance_from_engine_status` 落库。
- 为什么不用定时扫表：Beat 周期扫表粒度粗（运行结束后仍空转）、多实例扫表需要抢锁；自续投递把轮询间隔与单条运行的存活周期绑定，终态即自然熄火，不给系统留常驻负载。
- 一句话：**Outbox 解决「不丢」，自续投递解决「不悬挂」**——否则 Run 会永远停在非终态（代码注释原话）。

### Q14. 执行指标怎么归一？为什么要归一？

**答案要点**：

- 从引擎 `/job-info` 取真实行数 / 字节数（source_rows / sink_rows / source_bytes / sink_bytes），归一成控制面自己的指标快照（`application/execution_metrics.py`）。
- 为什么：README 的例子——「源 8 行 → 汇 4 行」这类差异必须可追溯；引擎各版本字段语义可能漂移，归一层把「引擎方言」翻译成「控制面事实」，下游监督规则只面对归一后的统一口径。
- 质量侧统计（reject_rows 等）同样经脱敏后并入快照（`runtime_supervision.py:88-96`）。

### Q15. 失败诊断是「再叫一次模型」吗？

**答案要点**：

- 不是。诊断是**确定性匹配**：失败类别 × 失败环节由规则匹配（`application/execution_diagnostics.py`），落库只写**脱敏文案**——不把含凭据线索的引擎原始报错直接入库或给前端。
- 设计理由：诊断要的是「稳定、可归因、可审计」的分类，而不是一次有创意的自然语言解释；同一类失败必须得到同一诊断，回归对比才有意义。

### Q16. 六条预算规则是哪六条？超了怎么办？

**考察点**：背数字（`application/runtime_supervision.py:6` 文件头注释直接列明）。

**答案要点**：

- 六条：**记录数（record_budget）、字节数（byte_budget）、超时（timeout）、输出比例（output_amplification）、拒绝率（reject_rate）、最小质量样本量**。
- `RuntimeSupervisor.evaluate()` 每轮从归一快照计算观测值：`observed_records = max(source_rows, sink_rows, records_written)`、`output_ratio`、`reject_rate = reject_rows / reject_sink_rows` 等，逐条与 hard limit 比对（`_hard_limit_matches`，命中即生成带 rule_id 与观测明细的告警）。
- 每轮评估产生**快照链**——监督历史不可篡改地串成链，事后可回放「什么时候开始偏离预算」。

## 六、Harness 内核

### Q17. Harness 是什么？它和上面的审批流程什么关系？

**考察点**：区分「业务审批」与「副作用治理」两层治理（`application/side_effect_harness.py`、`domain/harness.py`）。

**答案要点**：

- Harness 是内核级的**副作用治理框架**：任何真实副作用（写库、建表、发布等九类）都必须走 **Prepare→Approve→Commit** 三段式——先准备（不产生副作用）、再裁决（PDP 策略 + 人工/自动决定）、后提交。
- 与四眼审批的关系：四眼审批守的是「这个版本能不能上」，Harness 守的是「这个副作用怎么安全地落到真实系统」——审批是业务关口，Harness 是执行关口，两者都过了才碰生产。
- 典型案例：**Doris 影子表原子发布与回滚**——先写影子表，Commit 原子切换，失败回滚不留半成品。

### Q18. PDP 是什么？策略裁决怎么做的？

**答案要点**：

- PDP = Policy Decision Point（策略裁决点）：控制面里所有「能不能做」的判定收敛到一个组件（`application/harness_policy.py`），PEP（执行点，如 Tool Broker）只问 PDP 要答案、不自己写 if。
- 好处：策略集中可审计，新增规则不改调用方；策略输入是结构化上下文（角色、项目、操作、资源），输出是结构化裁决——与「模型建议」完全隔离。
- 生成侧的 `policy` 节点（`application/policy.py` `require_safe_generation_context`）是同一思想在图内的投影：进入下一步的资格由策略函数判定。

### Q19. 一次性 Capability 是什么？解决什么问题？

**答案要点**：

- Capability = 「做某件具体事的一次性令牌」：Prepare 阶段签发、只对本次副作用有效、用过即焚（`application/harness_access.py`、`tool_broker.py`）。
- 解决两个问题：① **重放**——同一条命令被重复投递（Outbox at-least-once 语义）时，旧 Capability 已失效，不会二次执行副作用；② **越权扩散**——令牌不含长期凭据、粒度细到单次操作，泄露面极小。
- 与 Tool Broker 配合：所有工具调用经 Broker 中转，Broker 校验 Capability + 问询 PDP 后才放行——「模型/服务想调工具」和「工具真的被调了」之间隔着两道门。

### Q20. Evidence Ledger 是怎么构造的？为什么用 Ed25519？

**考察点**：密码学基础 + 工程取舍（`application/evidence_ledger.py`、`infrastructure/harness_signing.py`）。

**答案要点**：

- 哈希链：每条事件计算 `canonical_sha256(sanitized_payload)`，并与 `previous_hash`（流上 `head_hash`）串联（`evidence_ledger.py:122-136`）——任何一条被篡改，其后所有 hash 全断。
- 签名：对事件 hash 做 **Ed25519 分离签名（detached signature）**，记录算法与 key_id（`evidence_ledger.py:143-164`）；密钥来自 `ETL_AGENT_HARNESS_PRIVATE_KEY / PUBLIC_KEYS` 配置，支持多公钥（轮换前置条件）。
- 为什么 Ed25519 而非 RSA：签名短、验签快、密钥短——审计事件高频签名场景下工程收益明显；PyNaCl 实现，避免手写密码学。
- 用途：关键治理事件（审批决定、副作用提交、监督告警）进入 Ledger 后成为**可验证不可抵赖**的证据链。

### Q21. Harness 里也有事务 Outbox，和执行监控那条是一回事吗？

**答案要点**：

- 同一模式、两个用途：`harness_outbox.py` 是通用命令投递通道（claim_pending / mark_sent / mark_failed），执行监控的自续投递是它承载的一个具体命令流（`harness_outbox_tasks.py` 经 `celery_app.send_task` 派发）。
- 模式要点三句话：**同事务写入保证不丢；认领-发送-标记保证至少一次；下游一次性 Capability / 幂等键保证重复投递不产生重复副作用**——这是面试里最容易被追问的闭环。

## 七、安全与凭据管理

### Q22. 数据库连接的密码是怎么保管的？明文会出现在哪里？

**考察点**：凭据生命周期（`application/secrets.py`）。

**答案要点**：

- SecretProvider 双实现：`FernetDatabaseSecretProvider`（对称加密落库，本地/单机）与 `VaultKvV2SecretProvider`（生产）；主密钥 `ETL_AGENT_SECRET_MASTER_KEY`，无效密钥直接抛 DomainError（`secrets.py:64-74`）。
- 凭据引用有防呆：已销毁的引用不能重新写入、预分配引用不能被其他内容占用（`secrets.py:91-94`）；销毁操作幂等（清密文 + 写销毁时间）。
- 明文边界三不：不落日志、不进 API 响应、**不进 LLM 提示词与图状态**；执行期凭据经 `credential_materialization.py` / `execution_credentials.py` 单向物化，只到 SeaTunnel 提交那一刻。

### Q23. 脱敏发生在什么时机？为什么是这个时机？

**答案要点**：

- 字段级脱敏发生在**样本返回之前、进提示词之前**：探查生成的 `DataProfile` 里样本行先过 `mask_sample` / `mask_value`（`application/masking.py:13-48`）才出 SecretProvider 边界。
- 为什么这么早：脱敏晚一步，敏感值就已经多一个出口（日志、LLM 上下文、Checkpoint 库都可能是泄漏面）；「在最靠近数据的地方脱敏」比「在出口统一过滤」的假设更少、更可靠。
- 同一原则贯穿全链：失败诊断文案脱敏、反馈给模型的引擎错误摘要脱敏——**脱敏不是功能，是不变式**。

### Q24. 身份认证是怎么做的？dev 和生产差在哪？

**答案要点**：

- 本地 `dev-header` 模式：请求头 `X-Actor-Id` 直接携带项目成员 `users.id`，方便联调。
- 生产：身份来自**可信网关（HMAC + Nonce）**，不接受请求方自述身份（README 明确）——Nonce 防重放，HMAC 防伪造，网关是唯一信任入口。
- 所有具名动作（申请、审批、提交）落到 actor_id 审计字段，与四眼审批的「利益分离」判定共用同一套身份事实。

## 八、工程化与可观测性

### Q25. 为什么要 Celery？为什么 API 和 Worker 分进程？

**答案要点**：

- 生成、探查、执行监控、Outbox 派发都是长耗时/后台任务，不能占着 HTTP 请求；FastAPI 只做同步受理 + 返回资源句柄。
- 三进程：API（uvicorn）、Worker（`celery -A etl_agent.worker:celery_app worker`）、Beat（定时调度）；Windows 下 `--pool=solo`。
- **Beat 必须单实例**（README 部署节）：周期任务的调度器多实例会重复触发；API 与 Worker 无状态可水平扩展，共享同一业务库。

### Q26. 为什么用两个数据库（业务库 + Checkpoint 库）？

**答案要点**：

- 业务库（PostgreSQL 17）存企业事实：连接、探查画像、版本、审批、执行记录——要事务与审计。
- Checkpoint 库只存 LangGraph 图状态——它的生命周期跟随「一次跑图」，写入模式是高频快照，与业务表完全不同。
- 分库收益：① 互不影响（Checkpoint 膨胀不伤业务查询）；② 权限可分离（业务服务不给 Checkpoint 写权）；③ 未来 Checkpoint 可整体替换后端而不动业务 schema。
- 诚实边界：Checkpoint 的 PostgreSQL 后端是占位实现（`agent/checkpoint.py`），当前降级内存 Checkpoint——README 已知边界，面试主动讲出来是加分项。

### Q27. 可观测性怎么做的？

**答案要点**：

- OpenTelemetry 全家桶：OTLP/HTTP 上报，FastAPI / httpx / SQLAlchemy / Celery **自动埋点**——跨进程（API → Celery → SeaTunnel REST）的链路自然串起来。
- 业务层指标：执行指标归一快照、监督快照链、Evidence Ledger 事件——三层从「技术链路」到「业务事实」都有迹可循。
- 健康检查 `/health`；API 挂 `/api/v1` 前缀共 60 条路径，Swagger 自动文档。

### Q28. 测试怎么做的？质量门禁有哪些？

**答案要点**：

- `uv run pytest tests`（单元测试）+ `ruff check / format --check`（lint 与格式）+ `mypy` **strict 模式**——三道门禁全绿才算过。
- mypy strict 对这个项目尤其重要：领域枚举、状态机、契约函数的类型签名就是「确定性关口」的静态证明。
- 端到端有真实链路脚本：`docker compose --profile e2e` 起 MySQL/SeaTunnel/Doris，`scripts/e2e/pipeline_run.py` 跑通源到汇。

## 九、高频追问与反问准备

### Q29. 「模型生成的配置质量差怎么办？会不会一直出垃圾？」

- 三道防线：共享修复预算（最多三份候选，`graph.py`）→ 契约校验拦截 → 引擎真实 `--check` 兜底；三道全过才有资格进审批。
- 反馈是定向的：格式错修格式（要求单个闭合 hocon 代码块）、策略错报策略项、引擎错报脱敏摘要——模型修的不是「再试一次」而是「知道错在哪」。
- 终态兜底：预算耗尽确定性 failed，错误信息含具体原因——宁可失败也不放行半成品。

### Q30. 「如果 SeaTunnel 挂了 / 执行卡住了，系统会怎样？」

- 提交失败：执行记录明确失败，不会留下「假运行」。
- 提交成功但引擎卡住：自续投递的监控命令持续拉 `/job-info`，同时**六条预算规则里的 timeout / 记录数 / 字节数**会先生成监督告警快照——运行不会无人知晓地悬挂。
- Outbox 崩溃恢复：命令在业务库同事务里，Worker 重启后重新认领 pending，投递不丢；重复投递被一次性 Capability 与幂等键吸收。

### Q31. 「这个项目最薄弱的地方是什么？」（诚实边界，主动讲）

按 README「已知边界」答：

1. LangGraph Checkpoint 的 PostgreSQL 后端是占位实现，当前降级内存 Checkpoint（重启丢恢复能力）；
2. Ed25519 密钥轮换与 Doris 原子发布尚未在真实生产环境验证；
3. SeaTunnel CLI 黑盒生成后端未实现，默认 `direct` 直连模型。
- 讲法建议：每条都带上「为什么当前可接受 + 补齐路径」，展示的是风险意识而非遮掩。
